讨论 Agent 时，很容易被复杂的架构图吸引。但如果想做一个可以理解、可以调试的小实验，可以先把问题缩小：一个程序如何根据反馈决定下一步？

下面是一个概念性示例，用来说明控制流程，不是可直接连接模型的 SDK 实现。

## 先定义任务的边界

假设任务是整理一组本地笔记。我们可以让系统读取给定目录、搜索文本、提出分类建议。第一版不需要允许任意命令执行，也不需要允许删除文件。

一个清楚的边界至少包括：可访问哪些数据，可调用哪些工具，什么情况需要停止，以及结果如何被检查。

## 一个最小循环

```python
def run_agent(task, model, tools, max_steps=8):
    history = [{"role": "user", "content": task}]

    for step in range(max_steps):
        decision = model.decide(history)
        if decision.kind == "answer":
            return decision.text

        if decision.tool not in tools:
            raise ValueError("Tool is not allowed")

        result = tools[decision.tool](decision.arguments)
        history.append({"decision": decision, "result": result})

    return "达到步数上限，请检查中间结果。"
```

这段伪代码强调三件事：行动来自一个明确决策；工具只从允许的集合中选择；循环有有限的步数。真实实现还需要处理结构化参数校验、超时、重复操作和错误恢复。

## 工具结果也是上下文

当一次搜索没有结果，系统需要知道“没有结果”，而不是把它理解为调用失败。同样，权限不足、参数错误和网络超时也应当被区分。

把工具输出设计成可辨认的结构，能让后续推理更清楚：

| 字段 | 用途 |
| --- | --- |
| status | 区分成功、空结果和错误 |
| data | 任务真正需要的数据 |
| error | 可理解的失败原因 |
| retryable | 是否适合重试 |

不要把未经筛选的整份日志交回模型。保留有用的信息，同时让完整日志可供开发者追溯。

## 先看过程，再看答案

一个答案看起来不错，并不代表过程可靠。可以记录每一步的输入、选用的工具、执行时长和结果状态，再检查它有没有重复寻找同一份信息。

对最初的原型而言，几条可读的轨迹比一个复杂的仪表盘更有帮助。先找出失败发生在哪里，再决定要不要增加记忆、规划或更多工具。

## 下一步的小实验

给同一个任务准备三种情况：信息完整、信息缺失、工具报错。观察系统是否分别给出答案、承认缺失、停止或恢复。一个能清楚说明自己没有完成什么的程序，比一个永远输出成功的程序更值得信任。
